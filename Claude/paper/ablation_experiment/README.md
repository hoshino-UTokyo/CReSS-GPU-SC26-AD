# Phase 3 Instruction Ablation Experiment

## 目的

Phase 3（CPUベンチマーク作成）の指示書のどの要素が作業完了時間に効いているかをテストする。
特にダンプ再実行を防ぐ要因の特定が重要。

## 実験スケール

- 1/10スケール: 15カーネル対象、シミュレーション36ステップ
- 対象カーネル: `target_kernels.txt` に記載

## バリアント設計（3パターン）

| Variant | ファイル | 指示内容 |
|---------|----------|----------|
| A. Minimal | `variant_A_minimal.md` | 目的 + テンプレート/チェックリスト |
| B. +Workflow | `variant_B_workflow.md` | A + 3段階ワークフロー |
| C. Full | `variant_C_safety.md` | B + variable_list仕様 + condition列 + inout判定ルール |

全バリアント共通:
- テンプレート、Makefile、チェックリスト、期待出力例、Special Cases（ベースライン）
- progress report指示あり（30分経過時に実験者が中断指示）

## 設計意図

テンプレート等を全バリアント共通にすることで、Stage 3（ベンチマーク作成）の作業効率差を排除。
差分が純粋にStage 1〜2（変数リスト作成・ダンプ）の違いに絞れる。

## 分離したい要因

| 比較 | 測定対象 | ダンプ再実行リスクとの関係 |
|------|----------|---------------------------|
| A→B | ワークフロー構造の効果 | カーネル毎にダンプ→一括ダンプ |
| B→C | safety rulesの効果 | inout誤分類/condition欠落→再実行 |

**最重要比較: B→C**（safety rulesがダンプ再実行をどれだけ防ぐか）

## セッション管理

- 30分で実験者が中断指示 → progress report作成
- 時間切りにより、セッション跨ぎの引き継ぎ品質も同時にテスト
- progress report指示は全バリアント共通（統制）

## 測定指標

- ダンプ再実行の回数
- 15カーネル完了までの総セッション数（総時間）
- セッション跨ぎ後の作業再開品質（手戻りの有無）
- ベンチマークの正答率（validation pass率）
